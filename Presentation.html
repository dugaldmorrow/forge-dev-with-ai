Agents plan, execute, and iterate toward goals

  • 🎯 Goal-directed — works toward a defined objective across many steps
  • 🔧 Tool use — reads/writes files, runs terminal commands, calls APIs, browses the web
  • 🔁 Reasoning loops — plans, executes, observes results, and adjusts
  • 🧠 Context-aware — understands your codebase, project structure, and prior work
  • 🤝 Human-in-the-loop — works with you, not just for you

An AI software development agent is fundamentally different from a code completion tool or a chatbot. The key insight is autonomy combined with tool use — the agent doesn't just suggest code, it executes a plan across multiple steps. Think of it as the difference between asking a colleague "how would you fix this bug?" versus handing them your laptop and saying "fix this bug and open a PR when you're done." The agent takes the second role.

  • New York Magazine (August 2025): software development is the most definitive use case of AI agents
  • Software development suits AI agents because: goals are clearly defined (tests pass, code compiles); feedback loops are fast; the environment is structured (files, APIs, CLIs); mistakes are recoverable (git)
  • The reasoning loop: observe codebase state → plan → execute (write code, run tests) → observe results → repeat until goal is achieved

Increasing levels of abstraction

Abstraction Level What you give the AI
Token / line (AI Coding Assistants) Cursor position — the AI completes your thought without being asked
Task / file (AI-Native IDEs) "Refactor this function", "add tests for this class"
Goal / feature (AI Dev Agents) "Implement this Jira ticket", "fix this bug end-to-end"
Intent / product (Autonomous Dev Platforms) "Build me an app that..."

The four categories of AI coding tools map directly to a familiar concept in software engineering: the abstraction ladder. We've always moved up it — from machine code to assembly to high-level languages to frameworks to no-code. AI coding tools are the next rung, and the four categories represent different positions on that ladder.

The key insight: the higher the abstraction level, the less the developer needs to specify *how* — they only need to specify *what*. This is also why higher abstraction tools are more autonomous: the AI must make more decisions independently to fill the gap between the high-level intent and the low-level code. In other words, autonomy level is an approximation of abstraction level — the star ratings you'll see on the next slide are a practical proxy for where each category sits on this ladder.

  • Token/line: the developer is still coding — the AI is accelerating keystrokes, not making decisions
  • Task/file: the developer directs; the AI executes a bounded piece of work within the session
  • Goal/feature: the developer delegates; the AI plans, iterates, and reports back
  • Intent/product: the developer describes the outcome; the AI handles architecture, implementation, hosting, and deployment

Autonomy is an observable proxy for abstraction level.

This slide makes the logical connection explicit: abstraction level and autonomy always move together because they are causally linked, not just correlated. You cannot have a high-abstraction, low-autonomy tool — if you say "build me an app", the tool must make decisions you didn't specify. There is no way around it.

The converse is equally true: a low-abstraction tool like autocomplete doesn't need high autonomy. It is completing your thought, not replacing your judgment. The developer is still fully in control — the AI is just a faster keyboard.

Specification beats vibes — especially for Forge

🎵 Vibe Coding 📋 Specification-Based Coding
How you start Describe a feeling or rough idea; iterate freely Write a spec first; agent implements against it
Best for Exploration, prototyping, learning Production apps, team handoffs, repeatable builds
Risk Drift, inconsistency, hard to reproduce More upfront effort — but predictable results
With Forge Fine for spikes; risky for manifests & scopes ✅ Recommended — Forge's constraints reward precision

"Before we look at the tools available, it's worth pausing on how you work with them — because the style of collaboration matters as much as the tool you pick."

Vibe coding — a term popularised by Andrej Karpathy in early 2025 — means describing what you want in loose, natural language and iterating until something clicks. It's a genuinely useful mode for exploration and learning. But it produces inconsistent results when the target environment has strict constraints — and Forge is exactly that kind of environment.

Forge has a declarative manifest, a fixed set of module types, a permission scope model, and a sandboxed runtime. When you vibe-code a Forge app, the agent fills in the gaps with its training data — and that data may be stale or simply wrong. You end up with a manifest that references deprecated modules, missing scopes, or a permissions model that doesn't reflect what the app actually does.

Specification-based coding flips this: you write down what the app should do (a brief spec, a README, or even a Jira ticket), and the agent implements against that spec. The output is more predictable, easier to review, and easier to hand off to a teammate or revisit in six months.

  • The resources folder contains a worked example of a Forge app specification — resources/app-specification-example/ — showing what a good spec looks like in practice
  • Vibe coding and spec-based coding are not mutually exclusive: a common pattern is to vibe-code a spike to explore the idea, then write a spec and regenerate properly before committing

The "Technical Cliff" is the point at which a vibe-coded app — one that looks complete and polished in a browser preview — hits the realities of production deployment. For general-purpose platforms like Lovable, Bolt.new, or v0.dev, the AI generates the app code, but everything else is left to the developer: setting up OAuth, provisioning hosting, managing scaling, wiring in Atlassian permission scopes, and handling deployment pipelines.

For a professional developer this is routine. For someone who used an Autonomous Dev Platform precisely because they wanted to avoid that complexity, it's a cliff edge — the moment the tool stops helping and the hard work begins.

  • Authentication: Atlassian OAuth 2.0 is non-trivial to implement correctly; Forge handles it out of the box with zero configuration
  • Hosting & scaling: general-purpose platforms generate front-end code; you still need a server, a CDN, and a scaling strategy; Forge runs on Atlassian's infrastructure automatically
  • Atlassian permissions: Forge apps declare scopes in manifest.yml and the platform enforces them; external apps must implement the full Atlassian permission model manually
  • Production deployment: Forge has a first-class deployment model (forge deploy); there is no equivalent in general-purpose platforms
  • The key message for this audience: if you're building for Atlassian products, App Studio is the only platform where the cliff doesn't exist — the platform handles everything that comes after the prototype

MCP Servers and Skills

Before we look at MCP Servers and Agent Skills individually, here's the big picture. The agent sits in the middle: it loads skills from local files to get instructions and workflow knowledge, queries MCP servers to get live data and capabilities from external systems, then sends an enriched prompt to the LLM. Neither MCP nor skills alone is sufficient — together they give the agent both the knowledge of how to work and the tools to act.

MCP connects any agent to any tool

MCP is the universal connector for AI tools — like USB-C for devices. Before MCP, every AI integration was custom-built. MCP means implement the client once, implement the server once, and any combination works. Three primitives: Tools (actions the agent can execute), Resources (data the agent can read), and Prompts (reusable instruction templates).

  • Created at Anthropic, released November 25, 2024; donated to Linux Foundation December 2025
  • OpenAI officially adopted MCP in March 2025; 1,000+ community MCP servers by February 2025, thousands today
  • Communication: JSON-RPC 2.0. Transport: STDIO for local servers, Streamable HTTP for remote servers

Skills load progressively

  1. Discover (~100 tokens) — agent sees skill name + description at startup
  2. Activate — agent loads full SKILL.md when the task matches
  3. Execute — agent follows instructions, loads referenced files as needed

If an MCP server is like giving the agent a phone to call external services, a skill is like giving the agent your team's runbook — the specific way your team does things. Progressive disclosure keeps costs low: only ~100 tokens per skill at startup, then the full instructions load only when the task matches.

  • Build a skill once, use it across Claude Code, Codex CLI, GitHub Copilot, and Rovo Dev — without modification
  • You can have many skills without burning tokens unnecessarily — cost scales with usage, not with skill count

  • Skills can be used to help ensure MCP is utilised reliably

The local/remote distinction is the clearest mental model for the skills vs MCP question. Skills are files on disk — they travel with your repo, they're version-controlled, and they load into the agent's context when the task matches. MCP servers are running processes that connect to external systems in real time: the Forge MCP Server, the Atlassian Rovo MCP, your database, your CI system. Neither is sufficient alone. Without a skill, the agent has to decide on its own whether to call the MCP — and it may not. Without the MCP, the skill's instruction to "look up the current module catalog" falls back to stale training data. Skills can also include executable scripts, so "local capabilities" covers more than just instructions — they can run commands on your machine too.

AGENTS.md gives every session a standing brief

The four-level hierarchy:

~/.rovodev/AGENTS.md          ← Global / personal (all your projects)
    └── ./AGENTS.md           ← Team (committed to repo, shared with teammates)
        └── ./src/AGENTS.md   ← Subdirectory (specialist rules for that area)
            └── AGENTS.local.md  ← Local override (gitignored, personal only)
Including an AGENTS.md reduced agent task completion time by 28% in a controlled study (ETH Zurich, 2025).

AGENTS.md is the "always-on" layer of agent configuration — as opposed to skills, which are "on-demand". You can create a hierarchy of these files but you probably shouldn't go overboard since it will fill up your agent context quickly leading to attention dilution and more tokens being consumed.

The hierarchy works by accumulation, not override: the agent reads all applicable AGENTS.md files from the outermost level inward, and concatenates them into a single brief. The global file (~/.rovodev/AGENTS.md) applies to every project on your machine — personal preferences, default tools, your name and role. The repo-level file (./AGENTS.md) is committed to source control and shared with the whole team — project overview, build commands, coding standards, agent boundaries. A subdirectory file (./src/AGENTS.md) adds specialist rules for that area only — e.g. "all code in this directory must use the payments API client, never raw fetch". The local override (AGENTS.local.md) is gitignored and personal — use it for machine-specific paths or experimental instructions you don't want to share. When all four exist, the agent sees all four, with inner files taking precedence on any conflicting instruction.

  • Rovo Dev: AGENTS.md / AGENTS.local.md (project); ~/.rovodev/AGENTS.md (global)
  • Claude Code: CLAUDE.md / CLAUDE.local.md (project); ~/.claude/CLAUDE.md (global)
  • Cursor: .cursor/rules/*.mdc (project); Settings > Rules for AI (global)
  • GitHub Copilot: AGENTS.md or .github/copilot-instructions.md (project)
  • Sizing: under 200 lines recommended (Anthropic guidance); a focused 50-line file outperforms a sprawling 1,000-line one

  • Add an .agentignore file

There are three ways to tell an agent to ignore files.

  • Click to show item 1 — The most portable option is an .agentignore file, which uses the same syntax as .gitignore.

A skill is just a markdown file with a YAML frontmatter block at the top. The frontmatter declares a name and description. That's what the agent reads at startup to decide whether the skill is relevant. The body of the file is only loaded when the task matches, which keeps startup token costs low.

  • Step 2 — Requirements.md: a structured plain-language spec. Sections typically include: what the app does, which Atlassian product it targets, which Forge module it uses, what data it reads/writes, and any UI/UX notes. Not a PRD — just enough for the agent to make correct decisions.
  • Step 3 — Rovo Dev in VS Code + Forge MCP: the Rovo Dev VS Code extension brings the agent into the editor so you can reference open files directly. The Forge MCP Server ensures the agent uses current module types and API scopes, not training data that may be months out of date.
  • Step 4 — spec-first debugging: when the agent produces something wrong, resist the urge to just fix the code. Ask: why did the agent make this decision? Usually the spec was ambiguous. Fix the ambiguity in Requirements.md, then re-run. This prevents the same issue resurfacing in the next feature.
  • The compounding benefit: after ten features, Requirements.md is a comprehensive, accurate spec that a new developer (or a new AI agent session) can use to understand the app immediately.
  • Transition: "That's how I do it — but it doesn't have to be all or nothing. Here are three levels of adoption you can use to ramp up at your own pace."

File Purpose Example contents

{AppName}.md Requirements for this app only — references the generic file and adds the app-specific detail YAML frontmatter (name, description), problem statement, Forge module & trigger, functional & non-functional requirements

# App Requirements
...
### Generic App Requirements
See GenericAppRequirements.md for generic app requirements.

### Functional Requirements
The app must listen to the creation of new comments on Jira
work items by subscribing to the `avi:jira:commented:issue` event.

The two-file structure keeps specifications DRY (Don't Repeat Yourself) and consistent. GenericAppRequirements.md is written once and covers the standards that apply to every Forge app in the project: TypeScript as the source language, Node.js 24, the /src/frontend/, /src/backend/, /src/shared/ directory layout, manifest.yml and package.json conventions, and the requirement for a Usage.md file. This file never changes between apps.

The app-specific file (e.g. EmailAddressDetector.md) uses a YAML frontmatter block at the top (name and description) so the agent — and any human reader — immediately knows what the app is. It then covers the problem statement, solution overview, key definitions, functional requirements (which Forge module and trigger to use, what the app must do), and non-functional requirements. It references GenericAppRequirements.md by name so the agent loads both files as context.

  • The YAML frontmatter mirrors the pattern used in SKILL.md files — it's the same "name + description for fast scanning" convention
  • Functional requirements are written as testable "must" statements: "The app must listen to...", "The app must not process..." — this precision is what prevents the agent from making assumptions
  • Definitions matter: the email detector spec defines exactly what a "personal email address" means and lists allowed prefixes — without this, the agent would guess
  • When a code review reveals an issue, the fix goes into the relevant section of the spec file first — adding a "must not", clarifying a definition, or adding a new constraint — then the agent is re-run with the updated spec
  • Transition: "With those two files in place, the agent has everything it needs — no verbal briefing required across sessions."
