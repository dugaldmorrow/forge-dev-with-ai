Agents plan, execute, and iterate toward goals

  • 🎯 Goal-directed — works toward a defined objective across many steps
  • 🔧 Tool use — reads/writes files, runs terminal commands, calls APIs, browses the web
  • 🔁 Reasoning loops — plans, executes, observes results, and adjusts
  • 🧠 Context-aware — understands your codebase, project structure, and prior work
  • 🤝 Human-in-the-loop — works with you, not just for you

An AI software development agent is fundamentally different from a code completion tool or a chatbot. The key insight is autonomy combined with tool use — the agent doesn't just suggest code, it executes a plan across multiple steps. Think of it as the difference between asking a colleague "how would you fix this bug?" versus handing them your laptop and saying "fix this bug and open a PR when you're done." The agent takes the second role.

  • New York Magazine (August 2025): software development is the most definitive use case of AI agents
  • Software development suits AI agents because: goals are clearly defined (tests pass, code compiles); feedback loops are fast; the environment is structured (files, APIs, CLIs); mistakes are recoverable (git)
  • The reasoning loop: observe codebase state → plan → execute (write code, run tests) → observe results → repeat until goal is achieved

Three primitives: Tools (actions to execute) · Resources (data to read) · Prompts (reusable instructions)

MCP is the universal connector for AI tools — like USB-C for devices. Before MCP, every AI integration was custom-built. MCP means implement the client once, implement the server once, and any combination works. Three primitives: Tools (actions the agent can execute), Resources (data the agent can read), and Prompts (reusable instruction templates).

  • Created at Anthropic, released November 25, 2024; donated to Linux Foundation December 2025
  • OpenAI officially adopted MCP in March 2025; 1,000+ community MCP servers by February 2025, thousands today
  • Communication: JSON-RPC 2.0. Transport: STDIO for local servers, Streamable HTTP for remote servers

Skills load progressively — ~100 tokens at startup

  1. Discover (~100 tokens) — agent sees skill name + description at startup
  2. Activate — agent loads full SKILL.md when the task matches
  3. Execute — agent follows instructions, loads referenced files as needed
Agent Skills are an open standard (agentskills.io, Apache 2.0), supported by Rovo Dev, Claude Code, GitHub Copilot, and Codex CLI.

If an MCP server is like giving the agent a phone to call external services, a skill is like giving the agent your team's runbook — the specific way your team does things. Progressive disclosure keeps costs low: only ~100 tokens per skill at startup, then the full instructions load only when the task matches.

  • Agent Skills are an open standard formalised at agentskills.io (Apache 2.0 licence)
  • Build a skill once, use it across Claude Code, Codex CLI, GitHub Copilot, and Rovo Dev — without modification
  • You can have many skills without burning tokens unnecessarily — cost scales with usage, not with skill count

The answer to "should I use an MCP server or a skill?" is almost always: both, for different reasons. MCP gives the agent capabilities — access to Jira, Forge docs, the web. Skills give the agent knowledge — your commit format, your pre-deploy checklist, your team's Forge patterns.   • Token cost: skills are much cheaper for encoding static knowledge; if information changes frequently or requires live data, use MCP instead

Skills = Local; MCP = Remote

Skills provide local knowledge and capabilities

MCP provide remote knowledge and capabilities

Skills can be used to help ensure MCP is utilised reliably.

The local/remote distinction is the clearest mental model for the skills vs MCP question. Skills are files on disk — they travel with your repo, they're version-controlled, and they load into the agent's context when the task matches. MCP servers are running processes that connect to external systems in real time: the Forge MCP Server, the Atlassian Rovo MCP, your database, your CI system. Neither is sufficient alone. Without a skill, the agent has to decide on its own whether to call the MCP — and it may not. Without the MCP, the skill's instruction to "look up the current module catalog" falls back to stale training data. Skills can also include executable scripts, so "local capabilities" covers more than just instructions — they can run commands on your machine too.

Transition: "MCP invocation isn't guaranteed — let's look at what that means in practice."

Agents choose whether to invoke MCP or skills

Developer asks: "What Forge module should I use for a Jira issue panel?"

Agent (without explicit instruction):
  Option A → call Forge MCP Server → get current answer  ✅
  Option B → answer from training data → may be outdated  ⚠️

The agent chooses Option B if it believes it already knows.

"Here's something that catches a lot of people out: just because an MCP server is configured doesn't mean the agent will use it. The agent weighs its own confidence against the cost of making a tool call — and if it thinks it already knows the answer, it skips the call. For Forge this is particularly risky, because Forge APIs and module types change frequently."

Skipping MCP or skills leads to predictable failures

Agent skips…What can go wrong
Forge MCP ServerUses a deprecated or non-existent module type from training data
Forge App Review skillMisses a missing API scope; deploys an app that fails in production
Atlassian Rovo MCP ServerReads stale Jira ticket data from context window rather than fetching live status
⚠️ Presence in the config is not the same as guaranteed invocation. The agent's internal confidence is the deciding factor.

These are the three most common failure patterns for Forge development. In each case the agent gave a fluent, confident answer — but it was wrong because it skipped the tool call.

  • Tell-tale sign: agent gives a fluent, confident answer about a Forge module or API that doesn't exist or has changed
  • How to spot it in Rovo Dev: check the tool call log — if forge-development-guide or search-forge-docs were not called during a Forge scaffolding task, the agent answered from memory

## Agent Rules  (AGENTS.md — enforced every session)
- You MUST consult the Forge MCP Server before selecting a Forge module type.
- You MUST invoke the Forge App Review skill before any forge deploy command.
- Never use training data alone for Forge manifest syntax or API scope decisions.

Vague prompts invite discretion; specific prompts enforce behaviour. The phrase "do not rely on your training data" is surprisingly effective. Better still: write the rule once in AGENTS.md and it applies automatically to every task in that project.
