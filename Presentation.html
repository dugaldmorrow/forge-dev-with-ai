AI agents pursue goals across many steps — they plan, execute, and iterate

  • 🎯 Goal-directed — works toward a defined objective across many steps
  • 🔧 Tool use — reads/writes files, runs terminal commands, calls APIs, browses the web
  • 🔁 Reasoning loops — plans, executes, observes results, and adjusts
  • 🧠 Context-aware — understands your codebase, project structure, and prior work
  • 🤝 Human-in-the-loop — works with you, not just for you

An AI software development agent is fundamentally different from a code completion tool or a chatbot. In August 2025, New York Magazine described software development as the most definitive use case of AI agents. The key insight is autonomy combined with tool use — the agent doesn't just suggest code, it actually executes a plan across multiple steps.

Think of it like the difference between asking a colleague "how would you fix this bug?" versus handing a colleague your laptop and saying "fix this bug and open a PR when you're done." The agent takes the second role.

The reasoning loop is critical: the agent observes the current state of the codebase, plans what to do, executes actions (writes code, runs tests), observes the results, and repeats until the goal is achieved.

Software development is a particularly strong fit for AI agents because:

  • Goals are clearly defined (tests pass, code compiles, acceptance criteria met)
  • Feedback loops are fast (run the tests, see if it worked)
  • The environment is structured (files, APIs, CLIs)
  • Mistakes are recoverable (git, version control)

Three primitives: Tools (actions to execute) · Resources (data to read) · Prompts (reusable instructions)

MCP was created at Anthropic and released November 25, 2024. In December 2025, Anthropic donated it to the Linux Foundation. OpenAI officially adopted MCP in March 2025. By February 2025, over 1,000 community-built MCP servers existed. Today there are thousands.

The USB-C analogy: before USB-C, every device had a different cable. Before MCP, every AI integration was custom-built. MCP is the standard connector.

Three primitives:

  • Tools (model-controlled) — executable functions; agent decides when to call them
  • Resources (application-controlled) — read-only data the agent can reference
  • Prompts (user-controlled) — reusable instruction templates

Communication: JSON-RPC 2.0. Transport: STDIO for local servers, Streamable HTTP for remote servers.

Agent skills load progressively — only ~100 tokens at startup, full instructions on demand

  1. Discover (~100 tokens) — agent sees skill name + description at startup
  2. Activate — agent loads full SKILL.md when the task matches
  3. Execute — agent follows instructions, loads referenced files as needed
Agent Skills are an open standard (agentskills.io, Apache 2.0), supported by Rovo Dev, Claude Code, GitHub Copilot, and Codex CLI.

Agent Skills are a concept formalised as an open standard at agentskills.io (Apache 2.0 licence).

The best analogy: if an MCP server is like giving the agent a phone to call external services, a skill is like giving the agent your team's runbook — the specific way your team does things.

Progressive disclosure is efficient: only ~100 tokens per skill at startup (name + description), then the full instructions load only when the task matches. You can have many skills without burning tokens unnecessarily.

The open standard means: build a skill once, use it across Claude Code, Codex CLI, GitHub Copilot, and Rovo Dev — without modification.

MCP Servers give the agent its tools. Skills give the agent its expertise.

The answer to "should I use an MCP server or a skill?" is almost always: both, for different reasons.

MCP gives the agent capabilities: access to Jira, access to Forge documentation, ability to run terminal commands, ability to browse the web.

Skills give the agent knowledge: your commit message format, your pre-deploy checklist, your team's preferred Forge module patterns, your architectural standards.

Token cost note: Skills are much cheaper than MCP servers for encoding static knowledge. If the information doesn't change often, use a skill. If it changes frequently or requires live data, use an MCP server.

Skills and MCP servers work best together — the skill orchestrates, the MCP provides live data

Forge App Builder SKILL
  └── instructs the agent to consult the Forge MCP Server
        └── which provides up-to-date module catalogs & manifest guidance
              └── agent generates correct, current Forge code
A skill without an MCP server relies on static knowledge. An MCP server without a skill relies on the developer prompting correctly every time. Together, they're self-sufficient.

This is the key synergy: the skill provides the workflow ("first, check the Forge MCP Server for the correct module") while the MCP server provides the live, accurate data.

Without the skill, the developer has to remember to prompt the agent to use the MCP server — and as we saw earlier, agents don't always invoke MCP servers unless told to. The skill bakes in the invocation instruction.

Without the MCP server, the skill's instructions to "look up the current module catalog" have nowhere to go — the agent falls back to training data.

MCP and skill invocation is discretionary — the agent decides whether to use them

Developer asks: "What Forge module should I use for a Jira issue panel?"

Agent (without explicit instruction):
  Option A → call Forge MCP Server → get current answer  ✅
  Option B → answer from training data → may be outdated  ⚠️

The agent chooses Option B if it believes it already knows.
Agent skips…What can go wrong
Forge MCP ServerUses a deprecated or non-existent module type from training data
Forge App Review skillMisses a missing API scope; deploys an app that fails in production
Atlassian MCP ServerReads stale Jira ticket data from context window rather than fetching live status
⚠️ Presence in the config is not the same as guaranteed invocation. The agent's internal confidence is the deciding factor.
  • This is one of the most practically important — and least documented — aspects of working with AI agents
  • The agent is not deterministic about tool use: it weighs its own confidence against the overhead of making a tool call
  • This is especially dangerous for Forge development because Forge APIs, module types, and manifest schemas change frequently
  • The tell-tale sign: the agent gives a fluent, confident answer about a Forge module or API that doesn't exist or has changed
  • How to spot it in Rovo Dev: check the tool call log — if forge-development-guide or search-forge-docs were not called during a Forge scaffolding task, the agent answered from memory

What to put in AGENTS.md: project overview + directory structure · build and test commands · coding standards specific to this project · agent boundaries and constraints (e.g. "never commit without explicit request").

Context files are the "always-on" layer of agent configuration — as opposed to skills, which are "on-demand".

Tool-specific naming:

  • Rovo Dev: AGENTS.md and AGENTS.local.md (project); ~/.rovodev/AGENTS.md (global)

  • Codex CLI: AGENTS.md with hierarchical discovery
