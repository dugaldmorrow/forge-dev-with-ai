Frequently Asked Questions

AI-Assisted Forge Development — Anticipated audience questions and suggested answers

🤖 Agents vs. Autocomplete & Tool Choices
Q1 Which agent should I actually start with — Rovo Dev, Claude Code, or Cursor?

Start with what you already have. If you're an Atlassian Cloud Standard, Premium, or Enterprise customer, Rovo Dev is likely already included — that's the obvious starting point because it has native Forge awareness and deep Atlassian context.

If you're not on a paid Atlassian plan, Claude Code (free tier) + Forge MCP Server is an excellent zero-cost starting point. If you already use Cursor, enable agent mode there — you don't need to switch.

The Forge MCP Server works with all of them. Your agent choice matters less than getting MCP configured.

Q2 Can I use Cursor or Windsurf as an agent, or are they just IDEs?

Both Cursor and Windsurf include an agent mode that can plan, iterate, and use tools — so they blur the category boundary. The distinction in this presentation is architectural: Cursor and Windsurf are primarily environments you code in, whereas Rovo Dev and Claude Code are agents that run alongside any editor.

In practice: Cursor's Composer in agent mode behaves like an AI agent. It can read files, run terminal commands, and iterate. The category label is a mental model, not a hard technical wall.

Q3 Is Rovo Dev available on the free tier, or do I need a paid Atlassian plan?

Rovo Dev Free gives eligible customers on Atlassian Cloud Standard, Premium, or Enterprise Jira plans 350 Rovo Dev credits per user per month at no extra cost — being gradually rolled out, with admins notified 30 days in advance. Rovo Dev Standard ($20/user/month) provides 2,000 credits with a 30-day free trial. Rovo Dev is not available on the Atlassian Free plan.

If you're on a Free plan or working outside Atlassian Cloud, Claude Code (Anthropic) has a free tier, and the Forge MCP Server requires no authentication at all — it's public documentation. That combination gets you most of the Forge-specific benefit at zero cost.

Q4 What's the difference between Rovo Dev and Rovo Studio / App Studio?

Rovo Dev (also accessible via the Rovo CLI) is an AI coding agent — it works in your terminal, reads your codebase, and helps you write and iterate on code. It requires developer involvement.

App Studio (also referred to as Rovo Studio) is a no-code path: describe what you want in plain language, review a generated spec, and deploy — no terminal required. It's aimed at admins, business users, and developers who want the fastest possible route to a working Forge app.

Think of it this way: Rovo Dev is for developers who want AI assistance while coding; App Studio is for anyone who wants a working app without writing code.

Q5 Why should I switch from GitHub Copilot, which I already use?

You may not need to switch at all. GitHub Copilot is an IDE extension — it augments your typing. The presentation isn't arguing against Copilot; it's introducing a different category of tool (agents) that does something Copilot doesn't: pursue multi-step goals.

You can use GitHub Copilot and get agentic capabilities. Copilot now has agent features in its newer versions. Alternatively, keep Copilot for in-editor autocomplete and use Claude Code or Rovo Dev for longer, multi-step tasks.

Also note: you can add the Forge MCP Server to GitHub Copilot's agent mode — so Copilot can give you Forge-accurate answers too.

Q6 Where does Devin fit if it's already fully autonomous? Why would I use anything else?

Devin is the most autonomous option on the market — it can take a GitHub issue and work on it independently for hours. The trade-off is cost and control: Devin starts at ~$500/month, and its fully autonomous mode means it makes architectural decisions without asking you.

For most Forge development, the sweet spot is supervised autonomy — an agent that does the work but checks in at decision points. Claude Code and Rovo Dev operate in that mode by default. Devin is better suited to well-defined, isolated tasks where you're comfortable with low oversight.

🔌 MCP Servers
Q7 Do I need to run the MCP server locally, or is it hosted somewhere?

The Forge MCP Server and Atlassian MCP Server are both remotely hosted at mcp.atlassian.com — you don't install or run anything locally. You just add the config block (shown in the slides) to your agent's MCP config file and restart.

Some community MCP servers (e.g. for GitHub, Linear, or custom internal tools) do run locally via stdio transport, which requires running a Node or Python process. But for the Atlassian servers, it's purely remote over HTTP.

Q8 What permissions does the Atlassian MCP Server get? Can it delete my Jira data?

The Atlassian MCP Server uses OAuth 2.1 — it inherits your existing Jira and Confluence permissions, nothing more. If you can't delete a Jira project in the browser, the agent can't either.

The agent can perform write operations (create issues, update pages) within your existing permissions. You should review what the agent proposes to do before it executes — most agents will describe actions before taking them if you configure them that way.

Always review agent-proposed writes before approving, particularly in production environments.

Q9 If MCP invocation is discretionary, how can I actually trust the agent is using it?

You can't guarantee it without enforcement. The three techniques covered in the presentation are:

  • AGENTS.md rules — write explicit instructions like "You MUST call the Forge MCP Server for any manifest or module type question. Never use training data alone."
  • @-mentions in prompts — some agents (Rovo Dev, Claude Code) let you @forge-mcp directly in the prompt, forcing invocation.
  • Skills with embedded instructions — encode the requirement in the skill file itself, so it applies automatically every time the skill activates.

After the fact, check the agent's tool call log — most agents show which tools were called during a session.

Q10 How do I know which MCP servers are trustworthy? Is there any vetting?

There is currently no central certification body for MCP servers. Community servers on platforms like mcpservers.org or smithery.ai are community-vetted but not formally audited.

For production use, prefer servers from established vendors (Atlassian, GitHub, Stripe, etc.). For community servers, check: is the source code public? Is it actively maintained? Does it request more permissions than it needs?

The Forge and Atlassian MCP Servers are first-party Atlassian products — they're the safest options for Forge development.

Q11 What happens if the MCP server goes down mid-task?

The agent will receive a connection error from the MCP client and will either retry, fall back to training data, or surface an error to you — depending on the agent's implementation.

For the Atlassian-hosted MCP servers, availability follows Atlassian's standard SLA for cloud services. Mid-task failures are rare in practice. The bigger risk is the agent silently falling back to (potentially outdated) training data without telling you — which is exactly why the AGENTS.md enforcement rules matter.

Q12 Can I build my own MCP server? How hard is it?

Yes — and it's surprisingly approachable. The MCP SDK is available for TypeScript, Python, Go, and Kotlin. A minimal server that exposes a few tools can be written in under 100 lines of TypeScript.

Common use cases for custom MCP servers: connecting the agent to an internal REST API, exposing a private database, or wrapping a proprietary CLI tool. The specification is open (now under the Linux Foundation), so the ecosystem of SDKs and tooling is growing quickly.

Search for "MCP quickstart" on the official Model Context Protocol docs at modelcontextprotocol.io for the fastest getting-started guide.

Q13 Is the Forge MCP Server always up to date, or could it lag behind the docs?

The Forge MCP Server pulls from developer.atlassian.com — the same source as the public Forge documentation. Atlassian maintains it as a first-party product, so it is updated in step with Forge releases. It should not lag significantly behind the official docs.

That said, very new features may take a short period to surface in the MCP Server. For cutting-edge capabilities, cross-check with the Forge changelog at developer.atlassian.com/platform/forge/.

Q13b Are both the Teamwork Graph CLI and Atlassian Rovo MCP Server both for connecting to Atlassian data?

Yes — and they are complementary, not interchangeable. Both access Atlassian data, and both can access the Teamwork Graph. The real distinction is about runtime and workflow pattern, not about which data they can reach.

  • Atlassian Rovo MCP Server (mcp.atlassian.com) is designed for hosted MCP clients — agents like Rovo Dev, Claude Code, or Cursor that connect via the MCP protocol. It covers Jira, Confluence, and Teamwork Graph tools, and is configured via your agent's MCP config file.
  • Teamwork Graph CLI (TWG) is designed for terminal/shell runtimes — agents or workflows that run commands locally. It wraps 15+ Atlassian products (Jira, Confluence, Bitbucket, JSM, Assets, Goals, Teams, Talent, and more) plus Teamwork Graph relationships, and is invoked as a CLI command.

Choose based on where your agent runs and how it calls tools:

  • If your agent uses MCP protocol (e.g. Rovo Dev, Cursor) → use the Rovo MCP Server
  • If your agent runs in a terminal or shell → use the TWG CLI

Both tools can access the Teamwork Graph. Neither is ranked above the other — they suit different agent runtimes.

📋 Agent Skills
Q14 What's the difference between an AGENTS.md file and a skill?

AGENTS.md is always-on context — it's loaded into every session automatically and provides standing instructions (project overview, coding standards, agent boundaries, build commands). Think of it as the agent's permanent briefing document for a project.

Skills are on-demand — they're loaded only when a task matches the skill's description. A "Forge App Builder" skill loads only when you're building a Forge app, not during every conversation. This keeps token costs low.

Use AGENTS.md for project-wide rules that always apply. Use skills for specific, repeatable workflows.

Q14b Do skills load at the start of a session, or can they load at any point?

Skills can load at any point within a session — not just at startup. Loading is demand-driven: the agent evaluates each skill's description field (~100 tokens) at session start, then loads the full SKILL.md only when a task matches.

In practice this means:

  • At session start — if your first instruction clearly matches a skill (e.g. "review my Forge app"), the skill loads immediately
  • Mid-session — if the conversation evolves and a new skill becomes relevant, it loads then (e.g. you start with a question, then ask to commit changes, so the commit skill activates)
  • Reactively — some skills are opt-in and only load on an explicit trigger (e.g. the quiz skill in this project only loads when you ask to be tested)

Because loading a skill consumes context window tokens, on-demand loading keeps costs proportional to usage — you only pay for what activates.

A skill loaded mid-session is just as effective as one loaded at the start — its instructions simply become part of the active context from that point forward.

Q15 How do I write my first skill? Is there a template?

A skill is a Markdown file with a YAML frontmatter header. The minimum viable skill looks like this:

---
name: my-skill
description: One sentence describing when this skill activates.
---

# My Skill

## Step 1: Do the first thing
Instructions for the agent...

## Step 2: Do the second thing
More instructions...

Save it to .agents/skills/my-skill/SKILL.md in your project. The agent picks it up automatically on next session start. Run npx skills add atlassian/forge-skills to install the official Atlassian bundle as a ready-made starting point.

Q16 Do skills work across all agents, or do I need different versions for Cursor, Claude Code, and Rovo Dev?

Skills stored in .agents/skills/ are natively recognised by Rovo Dev, Claude Code, Codex CLI, and GitHub Copilot without modification.

Cursor uses a slightly different format (.cursor/rules/*.mdc) and Windsurf uses .windsurf/rules/. The content is the same; the file location and minor syntax differs. A practical approach: maintain the canonical skill in .agents/skills/ and reference it from tool-specific locations to minimise duplication.

The agentskills.io standard (Apache 2.0) is designed for cross-agent portability — adoption is growing across the ecosystem.

Q17 npx skills add atlassian/forge-skills — does this work with Rovo Dev?

The npx skills CLI installs the skill files to .agents/skills/, which Rovo Dev reads natively — so yes, the skill files work with Rovo Dev.

However, the npx skills installer also attempts to auto-configure MCP servers. Rovo Dev manages MCP servers separately and does not support the auto-wiring step. After running npx skills add atlassian/forge-skills, follow the Rovo Dev-specific README to configure the Forge MCP Server manually in your Rovo Dev settings.

Q18 How often do I need to update skills, and what breaks if I don't?

Skills are static files — they don't update themselves. Run npx skills update periodically (e.g. monthly, or before starting a major project) to pull the latest versions from the registry.

If you don't update, the skill's instructions may reference outdated Forge patterns — e.g. module types that have been renamed, or UI Kit components that have changed. This is the most common cause of "why is the agent giving me outdated Forge module advice?" The fix is always: npx skills update forge-skills.

🏗️ Forge + AI Development
Q19 Is the code that agents generate actually production quality, or does it always need heavy cleanup?

Better than ever, but always review before deploying. With the Forge MCP Server providing accurate module types and manifest syntax, and the Forge App Review skill running a pre-deploy checklist, the rate of obvious errors drops significantly.

In practice: business logic and UI scaffolding tend to be high quality. The most common issues are in manifest API scopes (the agent may request more or fewer permissions than needed) and edge case handling. The Forge App Review skill specifically targets these failure modes.

Always treat agent-generated code as you would a PR from a capable but junior developer — review it, don't rubber-stamp it.

Q20 What are the most common mistakes agents make in Forge apps?

The five most common failure modes (covered in the hallucinations slide) are:

  • Wrong Forge module type — using a deprecated or non-existent module from training data (fix: Forge MCP Server)
  • Missing or incorrect API scopes in the manifest (fix: Forge App Review skill)
  • Deprecated UI Kit components — renamed or removed since training cutoff (fix: ADS MCP Server)
  • Incorrect Jira REST API version — mixing v2 and v3 calls (fix: Atlassian MCP Server + explicit version pinning)
  • Security misconfigurations — skipping permission checks in resolvers (fix: Forge App Review skill + human review)
Q21 Does this work with Custom UI Forge apps, or only UI Kit?

It works with both, but the benefits are stronger for UI Kit apps. UI Kit has a constrained, well-documented component set — the agent can't invent non-existent components, and the ADS MCP Server provides live component and token data.

Custom UI gives the agent much more freedom (it's essentially React in an iframe), which means more hallucination risk and less structural constraint. The agent can still scaffold Custom UI apps effectively, but you'll need to do more reviewing. The ADS MCP Server still helps by providing accurate design tokens and component guidance.

Q22 Can the agent run forge tunnel and actually see runtime errors, or does it just hand code back?

Yes — agents with terminal access (Rovo Dev, Claude Code, Cursor agent mode) can run forge tunnel, observe the output, read error messages, and iterate. This is the "agent iterates" row in the comparison table — the agent doesn't just generate code once; it runs it, reads the errors, fixes them, and retries.

This is one of the most powerful practical benefits: the agent can go through 5–10 tunnel-fix-tunnel cycles in the time it would take a developer to read the first error message.

Q23 How does the agent handle Forge apps that span multiple Atlassian products?

Multi-product apps are supported — the Forge manifest allows modules across Jira, Confluence, Compass, and others. The agent can scaffold these via the Forge MCP Server, which covers all products.

The main complexity is that each product has different module types and scopes. The Forge App Review skill should check that all scopes are correctly declared for each product targeted. With the Atlassian MCP Server connected, the agent can also read real data from each product to validate its implementation as it works.

Q24 What about testing — does the agent write tests, or just code?

Agents can write tests if you instruct them to. Neither the Forge MCP Server nor the forge-skills bundle currently include a dedicated testing skill, so test generation is driven by your AGENTS.md instructions and prompts.

Forge's testing story (unit tests via Jest, integration via forge tunnel) is well-understood — the agent can scaffold test files alongside code if you include a rule like "Always write Jest unit tests for resolver functions" in your AGENTS.md.

🎯 App Studio
Q25 What are the limitations of App Studio — what can't it build?

App Studio is best for simpler, well-defined apps — things like Jira issue panels, Confluence macros, or admin pages with straightforward logic. It struggles with:

  • Complex custom UI with significant frontend logic
  • Apps requiring custom resolver logic beyond standard CRUD patterns
  • Multi-product apps with intricate cross-product workflows
  • Apps integrating with external (non-Atlassian) APIs

For those cases, the developer agent workflow (Level 2) gives you more control. App Studio is the fastest path; the terminal agent is the most powerful path.

Q26 Who controls which App Studio apps get installed on our site? Can a developer deploy without admin approval?

Enterprise governance is built in. Atlassian admins control which apps can be installed on a site. For enterprise customers, App Studio includes approval workflows — a developer can build and submit an app, but an admin must approve deployment.

Internal/single-site apps (the most common App Studio use case) are governed by your existing Atlassian admin controls. The same policies that govern Marketplace app installation apply.

Q27 Is App Studio free, or is there a cost per app?

Internal and single-site Forge apps are mostly free under Forge's standard pricing — they stay within the free tier for most small-to-medium use cases. App Studio itself is included with Atlassian Cloud plans that include Rovo.

Costs arise if your app exceeds Forge's free invocation limits (which requires significant usage), or if it's listed on the Atlassian Marketplace (standard Marketplace fees apply). For internal tooling built with App Studio, cost is rarely a concern.

🔒 Security, Privacy & Cost
Q28 Does the AI agent see my actual Jira/Confluence data? Where does it go?

When the Atlassian MCP Server fetches Jira or Confluence data, that data is included in the agent's context window — which means it's sent to the LLM provider (e.g. Anthropic for Claude, OpenAI for Codex, Atlassian's own model for Rovo).

The data is only fetched when the agent calls the MCP tool — it doesn't continuously stream your Jira data. What gets sent is scoped to what you ask about.

Check your AI vendor's data retention and training policies before sending sensitive business data through an agent. Rovo Dev inherits Atlassian's data residency commitments. Other vendors vary significantly.

Q29 What's the data retention policy for agent-generated code and prompts?

This varies significantly by vendor:

  • Rovo Dev: governed by Atlassian's cloud data retention policies; subject to your organisation's data residency settings
  • Claude Code: Anthropic's commercial API terms apply; by default, prompts are not used for training (as of 2025)
  • Cursor / Windsurf: check each vendor's privacy policy; enterprise tiers typically offer stronger guarantees
  • GitHub Copilot: Microsoft/GitHub enterprise customers can opt out of code retention

For sensitive codebases, use enterprise tiers with explicit zero-retention agreements, or self-hosted models where available.

Q30 How much does running an AI agent cost in practice — per day, per feature?

Costs vary widely by agent and usage intensity. Rough ballparks (2026):

  • Rovo Dev Free: 350 Rovo Dev credits/user/month — included automatically for eligible Jira Cloud customers
  • Rovo Dev Standard: $20/user/month with 2,000 credits; overage at $0.01/credit; 30-day free trial available
  • Claude Code: ~$3–10/day for moderate developer use on the API (Pro plan is $20/mo with usage included)
  • Cursor Pro: $20/mo flat for most usage
  • Devin: from ~$500/mo; consumption-based at higher tiers

The strong trend is LLMflation — inference costs have dropped ~10x per year. Today's expensive use case is next year's commodity. Don't make permanent architecture decisions based on today's prices.

Q30b Does Rovo Dev include any free credits?

Yes — Rovo Dev Free gives you 350 Rovo Dev credits per user, per month. This is being gradually rolled out to customers on Atlassian Cloud Standard, Premium, or Enterprise Jira plans. Admins are notified 30 days before it's activated and can opt out if needed.

When you exhaust your 350 free credits, Rovo Dev stops working until the next billing cycle resets your allowance. To get more, an admin can upgrade users to Rovo Dev Standard ($20/user/month, 2,000 credits/month, overage at $0.01/credit).

Note that Rovo Dev credits are separate from core Rovo credits (used for Rovo Chat, Search, and Agents). The two pools don't share a quota.

Rovo Dev Standard also includes a free 30-day trial — worth starting there before committing to a paid plan.

Q30c As an agent session grows, does each query consume more tokens?

Yes — because AI models have no true memory. Every response requires the full conversation history to be sent as input. So query #20 includes all 19 previous exchanges plus your new prompt, making it significantly more expensive than query #1.

In practice this means:

  • Token cost increases throughout a session — each response costs more than the last
  • Context window fills up — there's a hard limit; once hit, early messages get dropped or the session stops working
  • Quality can degrade — important early instructions can get diluted in very long contexts

How to mitigate it:

  • Start fresh sessions for new, unrelated tasks — don't accumulate unrelated context
  • Use AGENTS.md / Requirements.md — key facts live in files, not the chat history, so a fresh session starts with full context at zero chat cost
  • Skills load on demand — they contribute only when needed, keeping idle sessions lean

The two-file spec structure in this workflow (GenericAppRequirements.md + {AppName}.md) is a direct response to this: rather than re-briefing the agent in chat every session, you load the spec files and the agent has everything it needs in a fresh, token-efficient context.

Q31 What about IP ownership of AI-generated code?

This is an evolving legal area and you should consult your legal team for definitive guidance. The general position as of 2026:

  • Most AI vendors' terms state that you own the output generated for you
  • The AI vendor does not claim ownership of code you generate using their service
  • Copyright in AI-generated content without human creative input remains legally unsettled in many jurisdictions

In practice, agent-generated Forge code is highly intertwined with human-authored prompts, AGENTS.md rules, and skills — the human creative input is substantial. Most legal teams are comfortable with this for internal tooling.

Q32 Our company prohibits using AI tools with production data. Can I still benefit from MCP?

Yes. The Forge MCP Server requires no authentication and accesses no company data — it only provides public Forge documentation. You can use it freely regardless of your company's data policies.

For the Atlassian MCP Server (which accesses your Jira/Confluence data), check with your security team. Many policies distinguish between production data and dev/sandbox data — Atlassian's sandbox environment is a good option for development without touching production content.

🚀 Getting Started
Q33 The config JSON you showed — where exactly does that file live for Claude Desktop vs. Cursor vs. VS Code?

Config file locations for MCP server configuration:

  • Claude Desktop (macOS): ~/Library/Application Support/Claude/claude_desktop_config.json
  • Claude Desktop (Windows): %APPDATA%\Claude\claude_desktop_config.json
  • Cursor: ~/.cursor/mcp.json (global) or .cursor/mcp.json in the project root
  • VS Code (GitHub Copilot): .vscode/mcp.json in the workspace, or user settings
  • Windsurf: ~/.codeium/windsurf/mcp_config.json
  • Rovo Dev: configured via the Rovo Dev settings UI or ~/.rovodev/config.json

After editing the config, fully restart the application — a simple reload is not sufficient for MCP config changes to take effect.

Q34 How long does it realistically take to go from zero to a deployed Forge app using this stack?

Realistic timelines based on the three levels:

  • Level 1 (MCP only): 10 minutes to configure; immediately more accurate Forge answers
  • Level 2 (full agent workflow): ~2 hours to set up; a simple Jira panel app can be built and deployed in under an hour once configured
  • Level 3 (App Studio): ~20 minutes from description to deployed app for a simple use case

For a developer who has never touched Forge before: Level 3 (App Studio) is the fastest path to a working app. Level 2 is better once you want to customise beyond App Studio's capabilities.

Q35 How do I convince my team or my manager to let me try this?

The most effective approach: demonstrate, don't argue. Take a real Jira issue that describes a small internal tool, give it to an agent with the Forge MCP Server configured, and show the result in under 20 minutes.

For security-conscious managers: point out that the Forge MCP Server requires no authentication and accesses no company data. Level 1 has essentially zero security surface.

For cost-conscious managers: Level 1 is free. Rovo Dev is included in existing Atlassian plans. The ROI argument is straightforward: if the agent builds a tool in 20 minutes that would have taken 2 days, the payback is immediate.

🔮 Future & Broader Questions
Q37 Will AI agents eventually replace Forge developers, or just change what they do?

Change what they do — at least for the foreseeable future. The agent handles the implementation details (manifest syntax, module selection, boilerplate, tunnel-and-fix cycles). The developer handles the things that still require human judgement: understanding user needs, making architectural decisions, reviewing output, and knowing when the agent is wrong.

The more accurate framing: AI agents are making Forge development accessible to more people, and making experienced Forge developers dramatically more productive. The job changes from "write all the code" to "direct, review, and ship."

Q38 Is MCP the standard that everyone's adopted, or could something else take over?

MCP has achieved very strong adoption in a short time: created by Anthropic (November 2024), officially adopted by OpenAI (March 2025), donated to the Linux Foundation (December 2025). Google has also moved toward MCP compatibility. The major AI labs are converging on it.

That said, technology standards can shift — particularly at the pace AI is moving. Google's Agent-to-Agent (A2A) protocol is a parallel standard for agent communication (as opposed to tool connection). The two are complementary rather than competing, but the ecosystem is still settling.

MCP is the strongest bet for tool connectivity today. It's the safe standard to build against.

Q39 What's Atlassian's long-term plan — building toward a world where no one needs to write Forge code manually?

The direction is clear: Atlassian is investing in a spectrum from no-code (App Studio) to full-code (Forge + AI agent), with the no-code end becoming more capable over time. Rovo Studio is evolving from "build an app from a description" toward full lifecycle management: spec → build → review → deploy → monitor.

Forge is also becoming a platform for hosting AI agents (Rovo agents are deployed as Forge apps), not just a target for AI to build. The long-term vision appears to be: agents building agents, with humans directing intent rather than writing implementation.

That said, complex custom business logic will require developer expertise for the foreseeable future. App Studio lowers the floor; it doesn't eliminate the ceiling.
